The real problem is not code. It is coordination between code that must change together.

Ask the room: who has waited for a token change to land in five repositories? That is the pain we are solving. The problem is not writing the CSS; it is coordinating five versions of the same decision.
Definition

What a monorepo is — and is not.

“

A monorepo is one repository that holds many independent packages and apps.

It is
  • One git history and one lockfile
  • Explicit package boundaries
  • Shared tooling and standards
  • Atomic commits across packages
It is not
  • One giant package
  • A flat folder with no rules
  • Automatic good architecture
  • The right choice for every team

Boundaries are the product. The repository is just the container.

Clarify the definition early. A monorepo is not "put everything in one folder". It is one history with clear package boundaries. The boundaries are what make it manageable.
Benefits

What it solves

Mostly coordination problems — not code problems.

01

Atomic changes

Token, component, story, and test change in one pull request.

02

One install

One lockfile and one dependency graph for the whole system.

03

Shared config

ESLint, TypeScript, and build settings live in shared packages.

04

No version skew

Internal packages always resolve to the local source.

05

Fast CI

Only affected work runs — when the graph and cache are set up.

06

Easy onboarding

One clone. One command. Every package is discoverable.

The win is leverage: one change can safely reach every consumer.

Notice that five of these six are coordination wins, not code wins. Faster CI is the only one that depends on how well we configure the tool. The rest come from the structure.
Trade-offs

What it does not solve

Every benefit has a maintenance cost. Name it, then control it.

CostControl
Boundaries are optional→Public exports + lint rules
CI gets bigger→Task graph + caching + filters
Ownership gets blurry→CODEOWNERS + clear package owners
One toolchain for everyone→Pin Node and pnpm at the root
Clone and install grow→Shallow CI clones + filtered commands

A monorepo is not automatically faster or cleaner. It is only as good as its rules.

Be honest about the cost. This slide sets up the rest of Part 1: the task graph and cache are how we control CI time; boundaries and ownership are how we control the codebase.

Both are good. Choose by constraints, not by hype.

Our choice

Turborepo. pnpm-native, about 30 lines of config, and enough for this design system. Nx is the better answer when you need generators and enforced boundaries at scale.

Avoid the tool war. Nx is excellent for large organisations that need generators, plugins, and enforced module boundaries. This repo is a focused TypeScript product monorepo, so Turborepo gives us the speed with much less ceremony.

Pipeline

The task graph is the build order

You do not list packages. Turborepo reads their dependencies.

@repo/tokens tokens → CSS / JS
→build
@repo/ui React components
→build
@repo/docs Storybook
@repo/playground Vite

Two consumers, one dependency. They can build in parallel.

turbo.json
{ "tasks": { "build": { "dependsOn": ["^build"], "outputs": [ "dist/**", "storybook-static/**" ] }, "dev": { "cache": false, "persistent": true } } }

^build means “build my dependencies before me.” One character, the whole graph.

The caret in ^build means "the same task in my dependencies". Tokens build before UI. UI builds before docs and playground. Turborepo infers the edges from package.json, not from a hand-written list.

Caching

A cache is a memo for tasks

Same inputs. Same hash. Same result. Skip the work.

)

Inputs are files. Env is configuration. Deps are upstream task hashes.

turbo run build
↓
hash the task
↓
seen this exact task before?
HIT Restore outputs milliseconds
MISS Run the task then save outputs

The cache does not guess. It matches content, not timestamps.

This is memoization for build tasks. If the task definition, the input files, the environment, and the upstream hashes are identical, Turborepo restores the outputs instead of running the task.
Caching

Make the cache trustworthy

A wrong cache is worse than no cache.

turbo.json · tasks
{ "build": { "dependsOn": ["^build"], "inputs": ["$TURBO_DEFAULT$", ".env*"], "outputs": ["dist/**", "storybook-static/**"] }, "typecheck": { "dependsOn": ["^build"], "outputs": [] }, "dev": { "cache": false, "persistent": true } }
01
Declare inputs.

Default is the package files. Add env files and global config that affect the build.

02
Declare outputs.

If it is not listed, it cannot be restored. Tests intentionally use an empty list.

03
Wire dependencies.

^build makes an upstream change invalidate downstream tasks.

04
Never cache side effects.

Dev, deploy, and publish are not cacheable. Mark them cache: false.

turbo run build --dry=json inspect hashes turbo run build --force ignore cache turbo run build --filter=@repo/ui one package
Inputs and outputs are the contract with the cache. If you forget an input, you get stale results. If you forget an output, Turborepo has nothing to restore. Use --dry=json to see exactly what goes into the hash.

Workspace strategy vs. backend strategy

Same system, different delivery. Choose by where the consumer lives.

Strategy A

Recommended

Build in the workspace. Publish from the workspace. Let the backend consume the artifact. The source of truth stays in one place; only the delivery changes.

This is the strategy conversation. If the consumer is inside the repo, workspace linking is the fastest and safest option. If the consumer is a backend service, an email renderer, or a mobile app in another repo, it needs a published artifact with a version. The hybrid is the usual answer: source-linked inside, versioned outside.

Habits

Rules that keep it healthy

Tools do not enforce architecture. Conventions do.

01

Apps never import apps

Deployables are leaves. If two apps share code, it belongs in a package.

02

Share through packages

No ../../ui/src. Import @repo/ui and let the boundary do its job.

03

One public entry

exports in package.json is the API. Everything else is private.

05

Root scripts are the interface

Versions and changelogs are generated from reviewed changes, not edited by hand.

Boundaries are a habit. Turborepo will not stop a bad import; code review must.

Turborepo does not enforce module boundaries the way Nx does. That is a deliberate trade: we get simplicity, but we need conventions and review. These six rules cover most of the day-to-day failure modes.

The rule

Reference only downward. Components never jump straight to primitives.

The three tiers are a dependency chain, not a hierarchy of importance. Primitives answer "what value?" Semantics answer "where and why?" Components answer "which part of this component?" The most common mistake is skipping the middle tier.

Naming is where most design systems fail quietly. If a token is named after a color, it cannot survive a rebrand. If it is named after a mode, it cannot switch modes. The order also matters: keep tier, domain, role, variant, state consistent so the name is predictable.

Field notes

Six ways to break the system

And the fix for each.

Raw values #4338ca → bg-accent

The token is the decision.

Dynamic classes bg-${variant} → cva({ variants })

Tailwind only sees static strings.

Mode in the name darkText → content.primary

Theme changes the value, not the name.

Skipping a tier {blue.700} → {semantic.color.accent.solid}

Component tokens reference semantic.

Editing output dist/variables.css → tokens/component/button.json

The next build will overwrite you.

Broken graph dependsOn: [] → dependsOn: ["^build"]

Stale builds are a graph problem.

Most failures are boundary failures. Fix the rule, not the symptom.

These are the mistakes I see most often. Raw hex is the obvious one. Dynamic Tailwind classes are the sneaky one. Mode-specific names and skipped tiers are the ones that hurt six months later. Editing dist is always temporary.
